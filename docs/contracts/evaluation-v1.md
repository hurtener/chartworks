# Evaluation and calibration v1

Status: implemented for review, 2026-09-22. Owns Phase 24 and the Phase 24 portions of EVAL-01 and EXP-01/03/05/09/10/11.

An evaluation suite is an immutable, versioned manifest with a nonzero deterministic seed, explicit fixture or live mode, protected input references, documented equivalent semantic outcomes, reviewed thresholds, hard case/call/token/retry/time ceilings and exact implementation/configuration/semantic/rule/template/source/dialect provenance. Cases compare semantic evidence digests and typed outcomes. They never treat SQL text similarity as result correctness. English and Spanish are explicit case attributes.

Security-critical cases cover signed identity and data scope, injection, dialect escape, resource exhaustion, BYO safety and frozen-report invariants. Their tolerated failure count is always zero. Thresholds are material in an immutable draft; they become executable only after a distinct authenticated reviewer accepts the exact revision and digest. A quality threshold requires at least one quality case. Owner calibration may instead be `unknown`; such a draft cannot become a passing gate. The evaluator contains a deliberately failing regression path so a green gate cannot be a no-op.

Fixture observations are embedded only in fixture suites. Live suites reject fixture observations and use the existing governed routing, NLQ planning/validation, chart and reporting services after protected input resolution. The evaluator reserves calls, tokens, retries and a deadline before delegation and checks the observation afterward. Reports preserve the mode, typed terminal status and separately record service, source and model duration, calls, tokens, retries and cost. Cancellation, timeout, budget exhaustion and dependency failure still produce durable evidence hashes. Missing cost or usage stays absent rather than becoming zero. Dialect entries independently say measured, unsupported or unknown; a fixture result cannot claim live engine evidence or public benchmark equivalence.

The runtime service reuses registered `ops.write`, `ops.read` and `ops.audit` actions plus signed tenant write/read/export/certify reach; it invents no issuer scope. HTTP, MCP and SDK expose suite author/review and run/read/cancel through that same service. PostgreSQL stores tenant-partitioned immutable suite revisions, distinct review receipts, run admission/cancel/terminal evidence and protected live inputs. Ordinary reports and logs contain hashes, bounded outcomes and measurements, never bearers, prompts, SQL or result rows. The production NLQ feedback adapter exports only reviewed active records into an immutable unassigned candidate ledger. A distinct authenticated reviewer must atomically partition that exact candidate into disjoint training and heldout children; a digest previously exposed as training cannot later become heldout evidence.

Each live input carries only an exact pack revision reference and cannot supply gateway configuration or cost. The effective model, role bindings, prompt instruction and pessimistic maximum cost per attempt live in a separate tenant-scoped runtime-pack record. Its author creates an immutable draft; a different authenticated reviewer must explicitly repeat and accept the exact runtime digest, configuration digest, model, role bindings and maximum attempt cost. A live run resolves only that accepted server-owned revision. The one gateway stamps its configuration digest into attempt receipts and charges the reviewed pessimistic cost before provider invocation, so an input or suite author cannot understate cost at dispatch time. Pack selection and rollback change the default pack for later production evaluation runs. Optimization accepts only live, passed, gate-passed reports with zero security failures and an exact reviewed heldout export lineage; fixture, failed, unreviewed and training-origin evidence is rejected.

Replay and shadow use the same evaluator. Optimization validates both reports, exact suite revision/digest/mode/seed and per-case held-out provenance before persisting a candidate proposal. Promotion derives the reviewer from signed authority and stores an immutable approve/reject receipt. Pack selection is a CAS pointer to an approved proposal; selecting an earlier approved proposal is the explicit rollback path. No score changes a prompt, example, rule or semantic publication.

The operator CLI runs or inspects explicit local fixture manifests. Live execution remains in the authority-bound runtime, where the existing single Bifrost gateway and source adapters are injected. Phase 34 consumes the suite/run hashes in its cutover ledger. Phase 25 still owns final live calibrated workloads and full release qualification.
